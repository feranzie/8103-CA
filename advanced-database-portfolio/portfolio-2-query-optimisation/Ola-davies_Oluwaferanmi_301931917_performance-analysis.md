# Portfolio 2: Query Performance Analysis

## 1. Setup

- **Database:** PostgreSQL 17: running in Docker
- **Dataset:** 50 doctors, 20,000 patients, 100,000 appointments, 40680 prescriptions, 20329 lab records (generated by `seed.sql`)
- **Method:** each query was run with `EXPLAIN (ANALYZE, BUFFERS)` before and after creating the indexes in `indexes.sql`. Each script was run twice and the second (warm-cache) run was recorded. Before indexing, only primary keys and the `no_doctor_double_booking` constraint existed.

## 2. Results

| Query | Before (ms) | After (ms) | Speed-up | Main plan change |
|---|---|---|---|---|
| Q1 Patient history | 21.199 | 0.179 | about 118x | Sequential scans became index scans |
| Q2 Doctor's schedule for a day | 0.543 | 0.125 | about 4.3x | Constraint index replaced by a composite index |
| Q3 Appointments per doctor (month) | 6.162 | 5.337 | about 1.15x | Sequential scan became a bitmap index scan |
| Q4 Pending lab requests | 7.271 | 0.342 | about 21x | Sequential scans replaced by a partial index scan |

## 3. Analysis

**Q1: patient history (118x faster).** Before indexing, the plan read `appointment` sequentially and then, for each of the 17 appointments found, scanned the whole `prescription` table and the whole `lab_record` table again (`loops=17` on both sequential scans). That is 34 full-table scans for one patient. The indexes `idx_appointment_patient`, `idx_prescription_appointment` and `idx_lab_record_appointment` turn each of those into a direct lookup. PostgreSQL does not create indexes on foreign key columns automatically, so these joins had no index until I added them.

**Q2: doctor's schedule (4.3x faster).** This query was not a full scan even before indexing. The planner used the index behind the `no_doctor_double_booking` constraint, which covers `doctor_id`, but that index cannot filter on the appointment time. It fetched 1,834 rows for the doctor and discarded all but 14. The composite index `(doctor_id, scheduled_start)` locates exactly those 14 rows and also returns them already in time order, so the sort step is no longer needed.

**Q3: appointments per doctor in a month (only 1.15x faster).** This query reads 24,800 rows, about a quarter of the appointments table, whichever plan is used. The index lets PostgreSQL skip the other three quarters, but the heavy work of fetching those rows, joining to `doctor` and grouping them remains. An index helps most when a query is selective, meaning it needs a small fraction of the rows. Here it is not selective, so the gain is small.

**Q4: pending lab requests (21x faster).** Before indexing, PostgreSQL scanned all 100,000 appointments and the whole lab table, joined them, sorted, and kept 50 rows. The partial index `idx_lab_record_pending` contains only rows with `status = 'requested'`, already ordered by `requested_at`. Because the query has `LIMIT 50`, PostgreSQL reads the first 50 index entries, looks up their appointments and patients by primary key, and stops. No sort is needed. The partial index is also small, because it holds only the pending rows.

## 4. Cost of indexing

Indexes are not free. Each one takes disk space and must be updated on every insert, update and delete of the indexed rows, which slows writes.

| Index | Size |
|---|---|
| idx_appointment_patient | 1168 kB |
| idx_appointment_doctor_start | 3104 kB |
| idx_appointment_start | 712 kB |
| idx_prescription_appointment | 880 kB |
| idx_lab_record_appointment | 464 kB |
| idx_lab_record_pending (partial) | 64 kB |

`idx_appointment_start` is the weakest index: it gives Q3 only a small improvement, so on a write-heavy system I would reconsider keeping it. The other five each give a large improvement to a query that matches the hospital's main operations.

## 5. Limitations

- Timings are single runs of a few milliseconds each on a 100,000-row dataset, so small differences (such as Q2 and Q3) can vary between runs. The large improvements in Q1 and Q4 are well beyond that noise.
- The data is randomly generated, so real clinical data with uneven patient visit patterns could behave differently.
- On a much larger dataset the gaps would widen, because sequential scans grow with table size while index lookups grow far more slowly.

## 6. Conclusion

Indexing the foreign key columns used in joins and adding a composite and a partial index brought the two most important operations (retrieving patient history and listing pending lab work) from tens of milliseconds to a fraction of a millisecond. The results also showed the limits of indexing: a low-selectivity query (Q3) gained little, and the best index for a query is the one that matches its filter, join and sort order together.
